# سجل تدقيق وقرارات التهيئة المؤسسية

**الحالة:** تدقيق مرحلة 0 مكتمل جزئيًا؛ لا توجد حزمة موحدة معتمدة أو مثبتة.
**تاريخ الفحص:** 2026-11-10
**المستودع:** `ccfb3cbdee650634f4a679ecaa75b2e55b574ed2` (`v0.6.12`) على `feat/schema-driven-review-filters`.

## الخلاصة التنفيذية

الموجود حاليًا تطبيق Electron مستقل مع قاعدة SQLite محلية غير مشفّرة، ومعالجة وثائق محلية أولية، ومحول API لـRAGFlow. التغليف الحالي NSIS للتطبيق فقط؛ لا يضم Runtime لـLinux أو Docker أو RAGFlow أو مزود Embedding، ولا يوجد مدير خدمات أو Compose خاص بالمنتج. لذلك لا يمكن اعتبار الإصدار الحالي «مثبتًا موحدًا» أو «حزمة Offline كاملة».

لم تُنفذ أي عملية تثبيت أو تنزيل صور أو نماذج في جلسة التدقيق. بيئة العمل Linux افتراضية ARM64 (نواتان وذاكرة 4 GiB) بلا PowerShell أو Windows أو WSL أو Docker daemon. هذه مواصفات حاوية التطوير وليست مواصفات جهاز الجهة، ولا تصلح لاختبار Windows أو اختيار حد أدنى مدعوم.

## خط الأساس البرمجي

- `desktop-app/package.json` يعرّف Electron Builder وهدف NSIS x64 واسم تطبيق واحد. ملفات الحزمة تتضمن واجهة التطبيق والعملية الرئيسية والعامل `worker.py` فقط؛ ولا تتضمن بيئة Python ومكتباتها أو أوزان Docling/PaddleOCR أو خدمات RAGFlow.
- `main.cjs` يوفّر تخزينًا مشفرًا لمفتاح RAGFlow عبر `safeStorage`، ويستخدم مسار IPC إلى العملية الرئيسية. إعداد BrowserWindow يحافظ على `contextIsolation` ويعطّل `nodeIntegration`.
- `offline-policy.cjs` يمنع اتصال Renderer والشبكة العامة من العملية الرئيسية، مع سماح محدود بطلبات RAGFlow على `127.0.0.1:9380` واتصالات التحديث المصرح بها. لم يظهر من فحص المصدر وحده سبب عطل Windows فعلي.
- `ragflow-adapter.cjs` يستهلك Health ورفع الوثائق وParsing وقراءة الحالة وRetrieval. وثائق RAGFlow 1.0.0 المنشورة توثق المسارات الأساسية المقابلة، لكن لا يوجد اختبار حي مع خادم أو مزود Embedding.
- قاعدة SQLite المحلية (غير المشفّرة) تظل مرجع البيانات الرسمي؛ لا يوجد مسار يكتب RAGFlow مباشرة فيها.
- ملفات Compose وRuntime Manager وWindows Service/Bootstrapper وInstaller متسلسل غير موجودة في المستودع.

## إصدار محرك المعرفة المرشح

وجدت واجهة الإصدارات الرسمية أن أحدث إصدار مستقر وقت الفحص هو **RAGFlow v1.0.0**، والوسم يشير إلى commit `db1cd5929a7885a3074547791f5ecc4d2f891739`. وهو إعادة كتابة Go مع تغييرات API واعتماديات تختلف عن الإصدارات السابقة؛ لا ينبغي أخذ Compose أو صور من فرع/إصدار آخر.

توصي وثائق RAGFlow بإعداد بدء يبلغ **4 أنوية CPU و16 GiB RAM و50 GiB مساحة حرة**، وتذكر Docker Engine 24+ وCompose 2.26.1+ و`vm.max_map_count=262144` لمحرك Elasticsearch الافتراضي. هذه توصية upstream وليست مواصفات دعم نهائية لمنتجنا، ولا يوجد Benchmark عربي أو حمل حقيقي يثبت أداء الجهاز المستهدف.

ملف Compose الرسمي يتضمن خدمات أساسية واعتماديات ومحركات متعددة عبر Profiles. كما ينشر منافذ الخدمة والخدمات التابعة؛ يجب تدقيق/تقييد جميع عمليات نشر المنافذ إلى Loopback قبل التوزيع. لم يُنسخ Compose إلى المنتج ولم يُعدّل أو يُشغّل، ولا توجد جردة Images/Digests مكتملة.

## قرار Windows/التشغيل

| الخيار | نتيجة التدقيق |
|---|---|
| Docker Desktop | غير مختار كمتطلب أو مكوّن معاد التوزيع. توثيق Docker يذكر أن الجهات الحكومية تحتاج اشتراكًا مدفوعًا؛ يلزم تدقيق الترخيص المؤسسي الفعلي قبل أي استخدام. |
| WSL2 مع Linux مخصص وDocker Engine | مرشح مبدئي لأجهزة Windows مستقلة، وليس قرارًا إنتاجيًا: systemd مدعوم، لكن Microsoft توضح أن خدمات systemd لا تُبقي مثيل WSL حيًا بذاتها. لا بد من اختبار آلية إقلاع وإبقاء الخدمة تحت حساب Windows وصلاحياته وبعد الخروج/إعادة التشغيل. إعداد boot command في WSL موثق لـWindows 11 وWindows Server 2022 فقط. |
| Linux VM | بديل يحتاج قياس موارد واختبار Lifecycle وتوزيع وترخيص على جهاز Windows فعلي؛ لم يُختبر. |
| خادم Linux داخلي | مرشح أكثر ملاءمة لخدمة مستمرة أو عدة أجهزة، لكنه يغيّر نمط التشغيل المحلي المستقل ويحتاج قرارًا تشغيليًا للجهة؛ لم يُعتمد. |

**القرار:** لا يُعلن اعتماد معمارية تشغيل نهائية قبل تجربة WSL2/Docker Engine على أجهزة Windows المستهدفة واختبار الإقلاع دون تسجيل دخول، الاستمرار بعد إغلاق التطبيق، الإيقاف الآمن، الاستعادة، وربط المنافذ. Docker Desktop مستبعد من الحزمة الافتراضية إلى أن يثبت الترخيص المناسب. إذا كان الاستخدام متزامنًا من عدة أجهزة، يجب تقييم خادم Linux مستقل بدل مشاركة SQLite عبر الشبكة.

## Embedding وLLM

BGE-M3 مرشح للاختبار لا للاعتماد: بطاقة Ollama الرسمية تعرض نسخة بحجم يقارب 1.2 GB، و1024 بُعدًا، وسياقًا يصل إلى 8192، بينما بطاقة Hugging Face تصف النموذج بأنه متعدد اللغات. هذه بيانات تعريف منشورة وليست اختبار دقة عربية أو قياس ذاكرة/سرعة على جهاز الجهة. توثيق RAGFlow v1.0.0 يصف Ollama/موفري النماذج المحليين ويذكر `qwen3-embedding:0.6b` مثالًا محليًا؛ يجب مقارنة المرشحين على مجموعة استعلامات ووثائق عربية مرخصة قبل تثبيت هوية النموذج.

لا يُضمّن LLM في هذه المرحلة: مسار التطبيق الحالي يسترجع المقاطع ولا يولد إجابات، لكن يجب التحقق عمليًا من إعداد RAGFlow/Embedding-only على الإصدار المنشور. تشغيل RAGFlow الكامل وفهرسة الوثائق دون مزود سحابي لم يُثبت.

## التحقق المنفذ

- `npm test`: 204 اختبارات، 203 ناجحة، صفر فاشلة، واختبار واحد متجاوز (بعد دمج إصلاحات updater على main).
- `npm run build`: ناجح؛ Vite أصدر تحذيرًا بأن حزمة JavaScript الرئيسية تتجاوز 500 kB بعد التصغير.
- أضيفت اختبارات تحقق محلية لاكتشاف مرشحي الحقول مع مصدر وصفحة، حفظ قرار المراجعة وسببه دون تعديل البيانات الرسمية، والفلاتر الديناميكية والفترة المرجعية وCSV مع تحييد صيغ الجداول.
- هذه فحوص تطبيق ومصادر فقط؛ اختبارات RAGFlow تستخدم استجابات محاكية. لم يُبنَ مُثبّت Windows ولم تُختبر Docker/WSL/OCR/Embedding/الفهرسة أو الاسترجاع الحي أو فصل الإنترنت أو إعادة تشغيل الجهاز.
- أُكمل في متابعة هذا الفرع ربط اكتشاف الحقول بمسار معالجة الوثائق، وإظهار المرشحين وقراراتهم داخل مركز الوثائق، وإكمال الفلاتر الديناميكية وتصدير النتائج إلى CSV/XLSX/PDF مع تضمين الفترة المرجعية. اكتشاف القيم يظل مرشحًا للمراجعة البشرية ولا يكتب إلى السجلات الرسمية.

## بوابات لازمة قبل إعلان المنتج أو توزيع المثبّت

1. تشغيل مراجعة توافق API كاملة على صورة RAGFlow v1.0.0 وCompose من الوسم نفسه، مع حساب ودataset ونموذج محلي، دون تعديل قاعدة RAGFlow مباشرة.
2. اختبار ميداني على Windows x64 فعلي يثبت Virtualization/WSL، موارد الجهاز، المنافذ، Lifecycle للخدمات، وقيود IT/الصلاحيات. لا يمكن استنتاجها من حاوية التطوير.
3. تدقيق Images وDigests وملفات تراخيص إعادة التوزيع لكل خدمة، واختيار محرك المستندات/البيانات؛ ثم تقييد النشر Loopback والتحقق من Compose الناتج بأداة Docker الرسمية.
4. تنزيل مرشحي Embedding من مصدر رسمي مع Revision/SHA256 وترخيص، ثم اختبار retrieval عربي مضبوط ومقارنة زمن/ذاكرة CPU، وتوثيق هل يلزم LLM لأي مسار مطلوب.
5. تصميم وتوقيع Runtime Manager وInstaller بعد حسم Windows lifecycle؛ ثم اختبار تثبيت/ترقية/إزالة محافظة على البيانات على Windows نظيف.
6. بناء SBOM وملف تراخيص وManifest للبصمات وحساب الحجم الفعلي قبل تسمية أي حزمة «Full Offline».
7. اختبار فصل الإنترنت فعليًا، إعادة تشغيل Windows، فهرسة وثيقة جديدة واسترجاعها، والنسخ الاحتياطي والاستعادة.

حتى اجتياز هذه البوابات، الحالة الصحيحة هي **التكامل البرمجي موجود جزئيًا؛ التثبيت المؤسسي وRAGFlow الحي وOffline غير مثبتة**.
